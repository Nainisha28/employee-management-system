# Employee Management System

A full-stack Employee Management System with employee CRUD, department transfers with automatic employee-code generation, global search, advanced filters, sorting, pagination, JWT authentication and role-based authorization.

- **GitHub repository:** `https://github.com/Nainisha28/employee-management-system.git`

## Tech Stack

| Layer | Technology |
|---|---|
| Frontend | Plain HTML, CSS, JavaScript (served by Spring Boot from `src/main/resources/static`) |
| Backend | Java 17, Spring Boot 3.4.3, Spring Data JPA, Spring Security |
| Database | MySQL 8.x |
| Auth | JWT (jjwt 0.12.6), BCrypt password hashing |
| API docs | Swagger UI (springdoc-openapi) and a Postman collection |

> **Note:** The frontend uses plain JavaScript with no build step, so there is no `package.json` or lockfile. It is served directly by the Spring Boot application.

## Features

- Employee create, view, edit and soft-deactivate (status becomes Inactive).
- Employee codes are generated by the server per department: IT `I0001`, HR `H0001`, Finance `F0001`, Sales `S0001`, Admin `A0001`.
- Department transfer: the employee gets the next code of the new department, the internal ID stays unchanged, same-department transfers are rejected, and every transfer is stored in the transfer history. Transfers run inside a database transaction.
- Global search across code, name, email, mobile, department, role, address and status. Aadhaar and PAN are deliberately excluded from search.
- Filters: department, role, status, gender, joining date, salary range. All filters and search work together.
- Sorting (ascending/descending) and pagination with 5, 10 or 20 records per page. The total matching record count is shown.
- Validation of all fields in both the browser and the API.
- JWT login with role checks for write actions.

### Salary range filter

| Option | Range |
|---|---|
| 1-3 LPA | 1,00,000 to below 3,00,000 |
| 3-5 LPA | 3,00,000 to below 5,00,000 |
| 5-10 LPA | 5,00,000 to below 10,00,000 |
| 10+ LPA | 10,00,000 and above |
| Custom | Minimum and maximum entered by the user |

The maximum value is exclusive and the minimum is inclusive, so every salary falls in exactly one band.

## Setup and Run

### 1. Create the database

```sql
CREATE DATABASE employee_management;
```

### 2. Set environment variables

Use your own MySQL password. Never commit real passwords.

**Windows PowerShell**

```powershell
$env:DB_URL="jdbc:mysql://localhost:3306/employee_management?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC"
$env:DB_USERNAME="root"
$env:DB_PASSWORD="YOUR_MYSQL_PASSWORD"
$env:JWT_SECRET="replace-with-a-random-secret-at-least-32-characters-long"
```

**macOS / Linux**

```bash
export DB_URL="jdbc:mysql://localhost:3306/employee_management?createDatabaseIfNotExist=true&useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC"
export DB_USERNAME="root"
export DB_PASSWORD="YOUR_MYSQL_PASSWORD"
export JWT_SECRET="replace-with-a-random-secret-at-least-32-characters-long"
```

| Variable | Purpose |
|---|---|
| `DB_URL` | JDBC connection URL |
| `DB_USERNAME` | MySQL username |
| `DB_PASSWORD` | MySQL password |
| `JWT_SECRET` | Signing key for JWT tokens (minimum 32 characters) |

### 3. Install dependencies

```bash
mvn clean install -DskipTests
```

Maven downloads everything listed in `pom.xml`. No JARs or `node_modules` are included in the submission.

### 4. Run the application

```bash
mvn spring-boot:run
```

On first start, Hibernate creates the tables (`employees`, `employee_code_sequences`, `employee_transfer_history`, `users`) and the default admin user is created.

### 5. Load sample data (optional)

After the application has started **once**, run these in MySQL Workbench or the `mysql` client:

1. `database/reference-schema.sql` (creates the `departments` and `roles` reference tables)
2. `database/seed.sql` (20 fictional employees and one sample transfer record)

Run `seed.sql` only on an empty employees table. Running it again may create duplicates or inconsistent data.

### 6. Open the app

- Application: http://localhost:8080
- Swagger UI: http://localhost:8080/swagger-ui/index.html

## API Documentation

- **Swagger UI:** http://localhost:8080/swagger-ui/index.html. First call `POST /api/auth/login`, copy the token, click **Authorize** and enter `Bearer YOUR_TOKEN`.
- **Postman:** import `postman/Employee-Management.postman_collection.json`.

| Method | Endpoint | Purpose | Access |
|---|---|---|---|
| POST | `/api/auth/login` | Log in and get a JWT | Public |
| GET | `/api/employees` | Search, filter, sort, paginate | Authenticated |
| POST | `/api/employees` | Create employee | Admin |
| GET | `/api/employees/{id}` | Get employee by ID | Authenticated |
| GET | `/api/employees/{id}/personal-details` | Personal and employment details | Authenticated |
| PUT | `/api/employees/{id}` | Update employee | Admin |
| DELETE | `/api/employees/{id}` | Deactivate employee (soft delete) | Admin |
| DELETE | `/api/employees/{id}/permanent` | Permanently delete employee and history | Admin |
| POST | `/api/employees/{id}/transfer` | Transfer to another department | Admin, Manager |
| GET | `/api/employees/{id}/transfer-history` | Transfer history of an employee | Authenticated |

### List query parameters

`search`, `department`, `role`, `status`, `gender`, `joiningFrom`, `joiningTo`, `minSalary`, `maxSalary`, `page`, `size`, `sortBy`, `direction`

Example:

```
GET /api/employees?search=Rahul&department=IT&minSalary=300000&maxSalary=500000&page=0&size=10&sortBy=employeeCode&direction=asc
```

`page` starts at 0. Allowed `size` values: 5, 10, 20 (anything else falls back to 10). Allowed `sortBy` values: `employeeCode`, `fullName`, `department`, `roleName`, `email`, `mobile`, `annualSalary`, `status`, `joiningDate`.

## Database

| Table | Purpose |
|---|---|
| `employees` | Employee personal and employment data. Unique constraints on `employee_code` and `email` |
| `employee_code_sequences` | Last used number per department, used to generate codes |
| `employee_transfer_history` | Old/new code and department, date and reason for every transfer |
| `users` | Login users (BCrypt password hash and role) |
| `departments`, `roles` | Reference tables created by `database/reference-schema.sql` |

### How employee codes work

Each department has a counter row in `employee_code_sequences`. On create or transfer, the counter is incremented and the code is built as department prefix plus a 4-digit number (for example `H0002`). Codes are never reused.

### How a transfer works

1. The employee and the target department are validated, and a transfer to the same department is rejected.
2. The next code of the new department is generated.
3. The employee's department and code are updated (the internal ID stays the same).
4. A row is added to the transfer history.

All steps run in one transaction, so they either all succeed or all roll back.

## Troubleshooting

| Problem | Fix |
|---|---|
| `Access denied for user 'root'` | `DB_PASSWORD` is wrong or not set in the same terminal you run Maven from |
| `Communications link failure` | MySQL is not running, or `DB_URL` has the wrong host or port |
| `Port 8080 already in use` | Stop the other program, or run with `--server.port=8081` |
| Login returns 401 | Check username/password, or the token has expired (8 hours) |
| `seed.sql` fails | Start the application once first so the tables exist |

## Known Limitations

- Aadhaar and PAN are validated but not encrypted at rest and not masked in API responses.
- Employees store department and role as text. `departments` and `roles` are reference tables without foreign keys.
- Only the Admin account is created automatically. Employee self-service restrictions are not implemented.
- Tables are created by Hibernate (`ddl-auto=update`) instead of versioned migrations.
- Employee code generation does not lock the counter row, so two simultaneous requests in one department could collide.
- No automated tests; testing is manual (see `TESTING.md`).
